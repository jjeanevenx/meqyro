# DO NOT DO

This is the most critical file for AI agents. Violating these rules can break production, expose user data, corrupt scoring, or introduce irreversible architectural debt.

---

## Architecture

**DO NOT move scoring logic out of `src/features/scoring/`.**  
Scoring must remain server-side and pure. Never put scoring in Route Handlers, client components, or Server Components directly.

**DO NOT import `src/features/*` modules in client components.**  
All feature modules use `import "server-only"`. Importing them in a client component will cause a build error — and rightfully so.

**DO NOT import `src/lib/supabase/server.ts` or any `createSupabase*` function in client components.**  
DB access is server-only. Client components fetch data through `/api/*` routes.

**DO NOT add a new architectural layer, pattern, or concept without a concrete need.**  
There is no DI container, no event bus, no CQRS, no separate domain objects layer. Do not introduce one.

**DO NOT bypass the state machine.**  
Session and order status transitions must always go through `assertTransition()`. Never update a status column with an arbitrary string.

---

## Security

**DO NOT hardcode secrets, API keys, or tokens anywhere in the codebase.**

**DO NOT put secret values in `NEXT_PUBLIC_*` environment variables.**  
These are bundled into the client and visible to all users.

**DO NOT derive market from locale.**  
`pt` locale does not mean Brazil market. `fr` does not mean EU market. Market is determined by geolocation or explicit user choice — not by language.

**DO NOT skip `timingSafeEqual` when comparing tokens or hashes.**  
Direct string comparison (`===`) enables timing attacks.

**DO NOT create a client-side path to unlock premium access.**  
Premium access must always be verified via a DB query for `result_access_grants`. There is no in-memory or LocalStorage override.

**DO NOT accept `price`, `amount`, or `currency` from the client request body in the checkout flow.**  
Price is always resolved server-side. Ignoring this enables price tampering.

**DO NOT disable webhook signature verification for testing or development.**  
In non-production environments, missing secrets trigger a simulated flow — they do not skip verification at runtime.

**DO NOT log full email addresses, raw session tokens, or payment amounts.**  
Use `logEvent()` with masked/redacted values. The logger auto-redacts common keys, but be deliberate.

---

## Data

**DO NOT modify `supabase/seed.sql` manually.**  
It is generated by `pnpm tsx scripts/build-seed-sql.ts` from `src/content/quizzes/`. Edit the content source files and regenerate.

**DO NOT edit existing migration files in `supabase/migrations/`.**  
Create a new migration instead. Editing applied migrations breaks reproducibility.

**DO NOT insert a result row more than once per session.**  
`completeQuizSession()` checks for an existing result and returns it if found. Do not break this idempotency.

**DO NOT store raw IP addresses.**  
Hash them with `hashIp()` using the server-side salt before any persistence.

---

## Quiz content

**DO NOT change question answer keys (`isCorrect`, `correctOptionId`) without documenting the change.**  
Changing a correct answer after questions have been answered in production invalidates existing results. This requires a scoring version bump and a documented decision.

**DO NOT leave a question without all four locale translations.**  
The content integrity test suite enforces this. A missing translation silently falls back and produces incorrect output for users.

**DO NOT add duplicate `stableKey` values within a quiz.**  
The test suite enforces uniqueness; duplicates break DB seed generation.

**DO NOT change question counts for a quiz in production without updating the scoring function.**  
BrainRank requires exactly 24 items. Personality Map requires exactly 40. These numbers are hard-coded assertions in the scorers.

---

## Scoring

**DO NOT change scoring logic without documenting the change in `docs/ai/DECISIONS.md`.**  
Scoring changes retroactively affect all unrecalculated results (results are stored by session; existing stored JSON is not recalculated unless a migration is run).

**DO NOT add non-determinism to a scoring function.**  
Given the same inputs, the same result must always be returned.

**DO NOT trust client-submitted score values.**  
The server always recalculates from raw answers.

---

## i18n

**DO NOT add a new key to the `Dictionary` type without adding it for all four locales.**  
TypeScript enforces this, but do not try to suppress the error with type casts.

**DO NOT use a third-party i18n library.**  
The project has a custom dictionary system. Adding next-intl, react-i18next, or similar would conflict with the existing architecture.

---

## Dependencies

**DO NOT install a payment provider SDK (Stripe SDK, InfinitePay SDK).**  
Both providers are called via raw `fetch()`. This is intentional to avoid SDK version lock-in and keep the bundle lean.

**DO NOT install an ORM (Prisma, Drizzle, TypeORM).**  
The Supabase client is the data access layer.

**DO NOT install a UI component library (shadcn/ui, Radix, MUI, Chakra).**  
All components are custom. Introducing a component library would require migrating the existing CSS system.

**DO NOT install an i18n library.**  
The custom dictionary system covers all four locales without external dependencies.

**DO NOT update transitive dependencies as a side effect of another task.**

---

## Code quality

**DO NOT use `any` to suppress TypeScript errors.**  
Fix the types properly.

**DO NOT add `@ts-ignore` or `@ts-expect-error` without a detailed comment explaining why it is unavoidable.**

**DO NOT use `console.log` or `console.error` directly.**  
Use `logEvent()` from `src/lib/observability/logger.ts`.

**DO NOT perform direct string comparison for security-sensitive tokens.**  
Always use `timingSafeEqual`.

---

## Tests

**DO NOT add `.skip`, `.only`, or `xit` to hide failing tests.**  
Fix the underlying issue.

**DO NOT weaken assertions (e.g. change `toBe(100)` to `toBeGreaterThan(0)`) to make a test pass.**

**DO NOT mock the module under test.**  
Mock its dependencies. Testing a mock is not testing anything.

**DO NOT remove tests because they conflict with a new implementation.**  
Update the test only if the business requirement genuinely changed.

---

## Scope

**DO NOT refactor code that is unrelated to the current task.**  
One task, one change set. Separate refactors require separate tasks.

**DO NOT reorganize folder structure without an explicit request and a documented reason.**

**DO NOT rename public API contracts (function signatures, type names, route paths) without confirming no consumers break.**

**DO NOT deploy to production or push to `main` as part of a documentation or analysis task.**
